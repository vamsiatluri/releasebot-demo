⚠️ This is how ReleaseBot itself gets deployed — not what ReleaseBot does. Two different pipelines, and they are easy to merge by mistake. The S3 bucket below is where this build stages its binaries. ReleaseBot touches no S3 and packages nothing: cutting a release is three GitHub calls — resolve trunk, create release/<version>, write a ledger row — and the mergeback opens the pull request back to trunk.     What their scope asks for here

    Migrating ReleaseBot from msnbc-dev to msnbc production

    The approach, written down before the work starts. The order exists because each phase removes a specific unknown — and three of them touch nothing in production at all, which is what makes the schedule survivable.

    Raise in week one, not week twelve. Phase 7's gate is production acceptance over roughly two release cycles. If the release cadence is monthly, Phase 7 falls outside a twelve-week engagement. Three ways to settle it: compress validation and cut over in week 6–7; hand Phase 7 over as a pre-approved runbook with a named executor; or extend. Any of those is fine. Discovering it in week eleven is not.
    The calendar is the real delivery risk. This is a newsroom. There will be a change freeze around election coverage, and another from mid-December. Both land inside a contract starting in late October — four to five of twelve weeks of change windows gone. The response is to front-load phases 1–4 into the freeze, because none of them touches production, and target cutover for the back half of November.

    the seven phases

    01

    Discovery — read the account, do not ask about it

    scripts/assess.sh msnbc-dev us-east-1 --prefix release reads every function, version, alias, role, inline policy, API stage and alarm into JSON, reviews it for blockers, and drafts a template from what is actually there.

    Output: an inventory nobody has to remember, and a diff target. Compare against docs/reference-capture/ — a known-good environment — so a difference means something.

    02

    Build the target account empty — zero production touch

    scripts/preflight.sh then scripts/bootstrap.sh. The preflight checks the things that cost a day each: both OIDC subject shapes plus the per-environment one, whether the repository can even carry a required reviewer, DNS hostnames on their VPC, the Lambda concurrency quota.

    Output: a running, empty ReleaseBot in the production account that nothing points at yet.

    03

    The pipeline, and prove it deploys

    OIDC rather than stored keys. Build once, deploy to test, read the fingerprint back off the running function, hold for a named human, promote the same bytes.

    Output: a green run that ends at the gate, with production untouched. That screenshot is the deliverable.

    04

    Parallel run — both accounts answering, nobody switched

    The old account keeps serving. The new one is driven with the same behaviour suite and the same signed payloads. assess.sh --against diffs the two and exits non-zero on a blocking difference, so it can gate a pipeline rather than a meeting.

    Output: "the production account behaves like the dev account" stops being an opinion.

    ★ Phase 04, actually run — two accounts, 2026-10-13

    ⛔ A separate ACCOUNT, not a second VPC — and the reason was learned the expensive way.

    IAM is global. An earlier attempt ran the target in a second region of the same account and collided on execution role names: releasebot-exec-cutrelease can exist once per account, not once per region. A parallel run inside one account cannot use the real names — so it cannot prove the thing it exists to prove. It is also what the engagement actually is: two accounts.

    ★ What the run found that nothing else would have

    That is the drift a hand-maintained account accumulates, and the comparison is the only thing that shows it. No template, no review and no green deploy would have told you. It is also the single best argument for running Phase 04 at all rather than treating it as a formality.

    Two smaller findings from the same run: the source runs the previous-generation runtime (provided.al2 against the template's al2023), and four log groups survive from throwaway network probes — the probe functions delete themselves, their log groups do not.

    ⛔ And the comparator itself was 39% noise

    iam/releasebot-dashboard-ApiRole-X1Lyy4HP4DBG   A: absent    B: present
iam/releasebot-dashboard-ApiRole-ttjoWT4DNnuB   A: present   B: absent

    The same role, from the same template, in two accounts. CloudFormation generates <stack>-<LogicalId>-<RANDOM> for any resource a template does not name, and that suffix can never match across accounts — so each one produced two permanent blockers. 12 of the first 31 differences were this.

    That matters more than the count. The parallel run exists to drive differences to zero and then trust the number. A comparator with a permanent floor of noise teaches people to ignore its output — so the noise is not cosmetic, it disables the control. Fixed by comparing stack-owned resources on their logical name: 14 blockers → 10, and every survivor is real.

    ⚠️ Scoped to stack-owned resources only. A hand-made role that happens to end in something suffix-shaped keeps its whole name — a false match between two different roles is the expensive direction; a false difference is merely noisy.

    Running assess for the first time found two more

    • The name filter hid five of six functions. --prefix releasebot — the obvious thing to type for a project called ReleaseBot — matched only the dashboard API, because the functions are named cutRelease, slackApprove and so on. It reported "1 functions, 1 roles, 1 APIs · 2 blockers": a thorough-looking read of one sixth of the system, and on day one in someone else's account it would have missed the application. The output of a filter that hides most of an account is indistinguishable from a small account. It now reports its own scope as a blocker when it drops more than it keeps.
    • It reported the hardening as the defect. Seven blockers said "holds secret values in environment variables" — five of them about functions that now hold ssm: references. The capture records names and never values, deliberately, so the review judged by name alone. A tool that reads identically before and after the work cannot show a control is in place, and worse, it tells the next person to undo it. It now classifies by the value's shape. 7 blockers → 1, the survivor real.

    How to re-run it

    scripts/assess.sh <source-profile> <region> \
  --against <target-profile> <region>

# exit 0 clean · 1 a blocking difference · 2 warnings · 3 the tool failed

    Read-only against both accounts, so it is safe to point at production — which is the whole idea. The inventory you can trust is the one taken from the running system, not from the templates somebody believes are current.

    05

    Cutover — move the pointers, not the system

    Slack slash commands and the Jira webhook are repointed. Everything else was already running.

    The URL is the migration. An execute-api URL contains the API id, and the API id changes when the API is recreated — which is exactly what this project does. Put a custom domain in front of it before cutover and this step becomes a DNS change instead of a console tour of every integration.

    Rollback is repointing them back. The old account is still running.

    06

    Soak — the part that cannot be compressed by wanting it

    Real releases, cut by real people, through the new account. Watch the dead-letter queue, the alarms, and whether anyone notices anything changed. The success criterion is that they do not.

    Output: evidence over elapsed time, which is the only kind there is.

    07

    Decommission — and prove it, do not report it

    Delete, then require describe-stacks to fail by name and every resource class to list back empty. A teardown that trusts an exit code is a teardown that reports success having deleted nothing — that is in sandbox-down.sh because it happened.

    Output: a closed account and a written record of what was removed.

    What transfers, and what does not

    The pipeline and the verification transfer. The infrastructure in this repository is a model built from the statement of work, not their system — do not deploy it at them. Read their account first, diff it against a working one, reconcile into their templates.

    Building a new environment from nothing

    One command, nine steps, in an account that has never held any of this. It was written from an account that already had everything — and its first run against a genuinely empty one found fifteen defects in a row, every one invisible where it was written. It now completes green, start to finish, and the run below is the proof rather than the claim.

    scripts/preflight.sh                      # before anything exists

scripts/bootstrap.sh \
  --profile msnbc-prod --region us-east-1 \
  --owner msnbc --repo releasebot \
  --vpc vpc-0abc --subnets subnet-a,subnet-b \
  --admin-email you@nbcuni.com --approvers U123,U456

    the nine steps

    1. Preflight — refuses to continue on a blocker.
    2. Artifact bucket — private, encrypted, public access blocked.
    3. Identity — the OIDC trust and four execution roles, deployed first and separately, so rolling the application back never rolls back the trust relationship the pipeline needs in order to roll it back.
    4. Network — a dedicated VPC, or only the security groups and endpoints inside one they already own. Nothing of theirs is created, so the stack is safe to delete.
    5. Artifact — built once, uploaded under a content-addressed key, and that key passed to the template.
    6. Compute — four functions, each behind a live alias.
    7. Edge — one API, two stages, WAF and throttle on production only.
    8. Configuration — Parameter Store per environment, so a published version freezes a pointer rather than the values.
    9. Observability, then the approval endpoint and the dashboard.
    It puts no credentials anywhere, deliberately. A bootstrap that takes secrets on its command line writes them into shell history on somebody else's laptop. Two separate scripts do that afterwards, and each refuses the other's token.

    What an empty account found

    Fifteen defects, in the order they surfaced. Each one had to be fixed before the next became visible — which is why a single run that goes green start to finish proves more than any amount of re-reading.

    1. The update script crashed on the first deploy — it assumed the stack already existed, so the one case it most needed to handle was the one it could not.
    2. A KMS error naming a key that is nowhere in the template. SSEEnabled: true on DynamoDB does not mean "encrypt this" — it is already encrypted. It means "use the managed key", which does not exist in a new account until something creates one.
    3. A new account's Lambda concurrency limit is ten, and AWS refuses any reservation leaving fewer than a hundred unreserved. The reservation that protects a mature account makes the stack undeployable in a fresh one.
    4. The retry loop hammered a dead stack six times. A failed create leaves ROLLBACK_COMPLETE, which can be neither updated nor created. It also blamed IAM for every failure — a retry that cannot tell a transient failure from a permanent one is a way of not reading the error.
    5. Content-addressed keys that nothing was told about. The digest is the whole point and is useless if the template still names the default.
    6. A correct DeletionPolicy poisoned every retry. The release ledger is retained on delete — right, for an audit record. So a rolled-back create left the table behind with no stack owning it, and the next create failed on it already existing, with no resource-level event naming it. Every failed attempt re-created the condition that made the next one fail. Bisected with a five-rung ladder, then proven both ways: with the orphan, the table alone fails; without it, the whole template creates.
    7. A disable switch two functions never saw. The concurrency reservation was read from a parameter in two places and hardcoded in two others. The switch looked like it worked. The lint written for it immediately found a third, in a different stack, four steps further on.
    8. A function pointing at a key nothing ever wrote. The approval function was missing from the upload loop while the build had been producing its artifact all along.
    9. ⛔ The green deploy that kept serving the old code. See below.
    10. A teardown that would have reported an empty account. Its stack list predated three stacks, so it would have left a CloudFront distribution, a Cognito pool, a VPC with a NAT Gateway, a table and a queue running — and printed "the account is empty", because it verified only the classes it already knew about.
    11. And then the fixed teardown failed on a bucket it had just emptied. CloudFormation cannot delete a non-empty bucket and will not empty one for you. Two things were wrong: the emptying ran after the stack deletes, and s3 rm --recursive removes current objects only — a versioned bucket keeps every old version plus a delete marker per object, so s3 ls reports an empty bucket that S3 refuses to delete.
    12. A detached ENI blocks the subnet, and the error blames the subnet. "The subnet has dependencies and cannot be deleted" — with no mention of an ENI anywhere. Two Lambda hyperplane interfaces sat in status available: detached, free, still a dependency. Lambda reaps them while the function exists; delete the function and nothing is left to do the reaping, so waiting never resolves it. The ordering is the subtle part — an ENI only becomes available after its function is gone, so the reaper has to run after the stack deletes and then retry.
    13. The configuration nothing owns. The per-environment Parameter Store values are written directly rather than by a template — on purpose, so a published version freezes a pointer to its config instead of the values. So no stack owns them and no stack delete removes them. The verification had been checking for them all along; the deletion had never been written.
    Both of the last two were found by a check that was already right. The teardown's verification knew what to look for before the teardown knew what to remove — which is the argument for writing the check even when you believe the cleanup is complete.

    Two more, found by using the thing rather than reading it

    • A dry run logged identically to a real one. cut: release branch ready  created=true — with dry_run only on a separate startup line in the same stream. During an incident that log says a branch exists when none does. It now sits on the action line.
    • A teardown-script edit cut a release candidate. The workflow ignores docs/** but not operator-only scripts, so a commit touching only a local cleanup script and this page cut a release and cancelled a production approval that was waiting. The trigger should be scoped to what changes the deployed artifact.
    Three of the fifteen are the same mistake wearing different clothes: trusting an operation's report instead of reading the resulting state. A content-addressed key uploaded but never referenced. A version published but never pointed at. A bucket emptied, but not of its versions.
    The one worth the interview: a green deploy that was not serving the new code.

    AWS::Lambda::Version publishes a new version only when the version resource changes. Its only property was a fixed description. So a deploy with a new binary updated $LATEST, left the live alias on version 1, created no new version, and reported UPDATE_COMPLETE.

    This is strictly worse than the content-addressed-key bug. There, the deploy changed nothing and went green. Here the deploy did change something, went green, and the change was not serving. Nothing in the stack status, the function's last-modified time, or the S3 object can tell you. The health endpoint still reported the previous commit — which is the only reason it was caught.

    Two fixes, and the second matters more. The description now carries the content-addressed key, so a changed binary forces a new version and the alias follows. And bootstrap reads the alias back — comparing the code hash the live qualifier actually serves against the artifact just uploaded, for all four functions, and failing if they differ.

      ✓ cutRelease live -> v2 serves the artifact just uploaded
  ✓ cutReleaseTest live -> v2 serves the artifact just uploaded
  ✓ releaseAutomationMergeback live -> v2 serves the artifact just uploaded
  ✓ releaseAutomationMergebackTest live -> v2 serves the artifact just uploaded
    A deploy is not finished when the deploy tool is finished. Every check in this project that found something real asked the destination. Every check that got fooled asked the transport.

    And a health endpoint that could not report its own problem

    Production answered 502 Internal server error while test answered 200. The log showed START / END / 1.25 ms and no error at all. The reason — GITHUB_TOKEN is required, which is the correct refusal before credentials are set — existed only in the response body of a direct invoke that nobody runs for another hour. Three things misled at once: a 502 is indistinguishable from a crash, the reason was invisible in CloudWatch, and /health, whose entire job is to report readiness, was the one endpoint that could not answer.

    HTTP 503
{"ok": false, "ready": false,

          running without credentials."}

    Now the failure is logged at INIT, /health reports unreadiness as data with the missing key named, and every other route still refuses — because a function with no credentials must not pretend it can cut a release.

    A public front door, private compute, and a signature as the boundary

    The API Gateway is REGIONAL — public. That is not an oversight, it is the only shape that can receive a webhook: a PRIVATE REST API is reachable only through an interface VPC endpoint, from inside the VPC, and Slack and GitHub are on the internet. What is private is the compute.

    For a webhook receiver the signature is the trust boundary, not the network. The network controls reduce cost and noise — without them anyone on the internet reaches the endpoint and is rejected, which still costs an invocation and a cold start before the HMAC is checked. They do not replace the signature.

    The four layers, in the order a request meets them

    1. WAF on the production stage. One rule, rate-per-IP, block above 300 requests per five minutes. That is abuse protection, not rate limiting — a newsroom cutting releases makes a handful of requests an hour, so anything near 300 is not a person. ⚠️ A web ACL binds to a stage, not an API, so "the API is behind WAF" is not a statement that can be true: production is protected and test is open, deliberately.
    2. An IP allowlist — built, parameterised, and switched off. See the asymmetry below for why.
    3. HMAC verification, in the function. SHA-256 over Slack's base string, compared with a constant-time compare rather than == (which leaks the match position through timing), plus a replay window on the timestamp. Jira uses a shared-secret header. This is the actual authentication.
    4. Private subnets. Outbound egress via NAT and VPC endpoints; nothing inbound. Nobody reaches the compute — they reach API Gateway, which invokes it.

    Two of the three inbound sources are allowlistable. One is not.

    Measured from the providers' own published ranges, not assumed:

    SourcePublished rangesAllowlistable
    GitHub webhooks9 CIDRs✅ trivially
    Jira CloudAtlassian publishes egress ranges✅ yes
    Slacknone❌ no
    GitHub Actions runners7,036 CIDRs❌ why the test stage stays open

    So only the Slack path has to be open to the internet. That is a concrete recommendation rather than "we should lock it down" — two of three paths can be narrowed at zero behavioural risk. And it explains the shape of the policy: a REST API has exactly one resource policy, so the per-stage split lives in the Resource element.

    Endpoint type is not reachability, and conflating them is the mistake worth not making. REGIONAL means public DNS; a resource policy can still refuse every source but CloudFront or a named CIDR. The assess tool now captures the resource policy and the per-stage WAF association for exactly this reason — it used to report the endpoint type and leave the only question that matters to be guessed at.

    Can Slack talk to a private API? Not directly — and "no way" is still wrong

    Three routes exist, and one of them keeps Lambda.

    1. Socket Mode. The app opens an outbound WebSocket and receives slash commands and button clicks over it. No inbound endpoint at all. ⛔ It needs a long-lived connection, so ECS/Fargate, not Lambda — you trade the serverless footprint to delete the public surface.
    2. Poll Slack instead. ★ This one keeps Lambda. Every Slack Web API call is outbound, so a scheduled function needs nothing inbound and no container. ⚠️ The honest catch: a Block Kit button click is delivered only to a request URL or over Socket Mode. So polling cannot carry the approve button — but it can carry an emoji reaction, which is attributed, timestamped, and sits permanently in the channel beside the request. Arguably a better audit record than a button press.
    3. Front the private API with CloudFront or an ALB. Buys WAF and Shield at the edge and an API unreachable directly — but moves the public surface rather than removing it.

    Two that sound right and cannot work: a REQUEST Lambda authorizer never receives the request body, and Slack signs the body; and mutual TLS is supported on a custom domain but neither Slack nor GitHub presents a client certificate. Lambda@Edge can do it — a viewer-request function with IncludeBody gets up to 40 KB — and is probably not worth the complexity against a WAF rule that simply requires the signature header to be present.

    What is actually in the VPC — four functions, two network interfaces

    Read from the live account, because the names mislead:

    CountTypeWhat it isSecurity group
    2lambdaAWS Lambda VPC ENI-…, one per availability zonethe Lambda SG
    4vpc_endpointtwo interface endpoints × two AZsthe endpoint SG
    1nat_gatewayin the public subnetnone — NAT gateways take no SG
    ⚠️ The Lambda ENI's name is misleading, and it matters.

    It reads ENI-releaseAutomationMergeback, which looks function-specific. It is not. A Lambda VPC ENI is shared by every function with the same (subnet set + security group set) — the description merely names whichever function caused it to be created first.

    Four functions are attached here — cutRelease, releaseAutomationMergeback, slackApprove and the dashboard API — all with identical subnets and SG. So there are two interfaces, one per AZ, not eight.

    Who creates them, and who may delete them

    ENIRequesterRequesterManaged
    Lambdaan assumed-role session — Lambda assuming the function's own execution rolefalse
    VPC endpointan AWS service accounttrue
    NAT gatewayan AWS service accounttrue

    None of them is attached to an EC2 instance — every Attachment reads amazon-aws, meaning AWS-managed infrastructure: Lambda's Hyperplane fleet, the endpoint service, the NAT gateway. The account owns them; AWS holds them.

    ★ That the Lambda ENI is requested by an assumed session of the function's own execution role is why AWSLambdaVPCAccessExecutionRole must be on the role before a function can be VPC-attached — and why omitting it fails with an error naming CreateNetworkInterface rather than naming the policy.

    And this is what broke the teardown. RequesterManaged: false on the Lambda ENIs means they are yours to delete, which is what the teardown's reaper does. The endpoint and NAT ENIs are true — they go only when the endpoint or NAT goes. So a teardown has two different jobs, and getting that wrong leaves a detached interface holding a subnet hostage with an error that blames the subnet.

    ⚠️ One practical consequence: a fifth VPC function costs no new interfaces if it uses the same subnets and SG. Change either and you get a fresh pair — plus the old pair lingering until Lambda reaps them.

    ⛔ The biggest hole was not the network. It was the secrets.

    The Slack signing secret and a 93-character GitHub token were plaintext Lambda environment variables across five functions, with no customer-managed key. Three consequences, and the first is the one that matters:

    1. Anyone with lambda:GetFunctionConfiguration read them, in the console. No network control touches this.
    2. A published version freezes configuration as well as code — so every secret was frozen into every version, and rotating one silently invalidated every older version as a rollback target, which is the day you need one.
    3. The value travelled through a CloudFormation parameter, and therefore a change set, and therefore anything that archives change sets.

    They now hold a reference — ssm:/releasebot/<env>/secrets/<name> — resolved at INIT from a SecureString. A value with no scheme is returned unchanged, so the local harness, the contract tests and the dev account keep passing literals and the handler code is identical in both worlds. The Live tab reports which mechanism each stage is actually using.

    A partly migrated function reports neither. It reads mixed (1 of 2), never reference — a half-finished rollout that displays as hardened is worse than one that displays as plaintext.

    Two traps found doing it

    • The kms:Decrypt condition named the wrong service. All four roles scoped it to ViaService: secretsmanager only — but a SecureString decrypt goes via SSM. That silently refuses it, and the failure is an AccessDenied naming KMS, so the instinct is to widen the key policy, which cannot fix a wrong condition.
    • The secrets live one level down, under /secrets/. The config reader walks /releasebot/<env>/ non-recursively with decryption, so a secret stored as an immediate child is pulled into memory on every INIT for nothing.

    ★ And a claim that turned out to be wrong

    "Rotation is a Parameter Store write with no deploy" is not true, and the test caught it: after the parameter was already correct, a correctly-signed request still returned 401 — the warm execution environment had resolved the old secret at INIT and kept serving it.

    Worse, the obvious fix is also a no-op: publish-version returns the existing version when nothing has changed. There is no API to force a cold start. So the rotation script bumps a marker variable, publishes, and moves the alias — the secret stays a reference and the artifact is untouched, but it is a deploy, just a configuration-only one.

    What references genuinely buy, and this part stands: the secret is absent from the function config, the console and every change set; an older version is no longer stranded as a rollback target, because it holds a pointer and reads the current value when it next starts; and rotation never rebuilds the artifact.

    Proven, not described

    A correctly-signed slash command on the production stage — signing secret and write token both resolved from SecureStrings — created a real release branch, which was then deleted.

    ✓ correctly signed  -> HTTP 200, command accepted
✓ wrong signature   -> HTTP 401
✓ valid sig, 1h old -> HTTP 401   (replay window enforced)
    A positive control alone proves nothing here. HTTP 200 is also what a function that verifies nothing returns. Only the pair — a correct signature accepted and a wrong one rejected — proves the check is on. The script also asserts on the response body: a 200 carrying a refusal is not a pass, and checking only the status code reported a reversed argument order as success.

    What is still open, in the order I would do it

    1. WAF does not reject unsigned requests. A request with no signature header still invokes the function, which then rejects it — paying an invocation and a cold start to say no. A rule requiring the header blocks it for free. Best win for the effort.
    2. WAF has one rule. No managed rule groups, no body size cap.
    3. WAF logging is off. There is currently no way to tell whether anyone has ever probed the endpoint.
    4. No alarm on signature failures. Three alarms exist — queue depth and two contract checks — and none fires when someone hammers the endpoint with bad signatures. That is the signal that says you are being probed.
    5. A customer-managed key instead of the AWS-managed SSM key, so kms:Decrypt can be scoped by key policy and CloudTrail is per-key.
    Items 3 and 4 are not prevention. They are the difference between being secure and knowing you are.
