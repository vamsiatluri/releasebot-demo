    What their scope asks for here

    How the pause gets lifted

    The release stops on its own and waits for a person. Two routes can lift it — one is the control, the other is a convenience built on top of it. They are not equivalent, and the difference is stated rather than smoothed over.

    primary · proven

    Approve in GitHub

    An environment protection rule names the reviewers. GitHub holds the job, emails them, and refuses to start production until one of them clicks approve.

    • ✓ Enforced by GitHub, not by a condition inside the workflow — editing the workflow does not remove it
    • ✓ The approver is a named GitHub identity, and the decision is in GitHub's audit log
    • ✓ Observed holding a real production deploy in this account
    optional · proven

    Approve from Slack

    The pipeline posts the pause into a channel with a button on it. Clicking the button calls the same GitHub approval the reviewer would have clicked.

    Why one of these is weaker, said plainly

    GitHub's rule says only these named people, signed in to GitHub. A chat button says anyone who can click in this channel, and GitHub records the approval as the service account that holds the token rather than the person who decided. The identity check moves out of GitHub and into our own code — so that code verifies the request really came from Slack, checks the clicker against an explicit list, and writes down every attempt.

    It is deployed as a separate stack for exactly this reason: deleting that one stack removes the chat route and leaves GitHub's gate untouched. If a reviewer objects to the button, that is the whole remediation.

    The last step, and why it is a good find Those are real lines from the endpoint's own audit log, from a real click. Every link we built holds — delivery, signature, approver, run id — and GitHub refuses at the end. A fine-grained access token is not permitted to review pending deployments at all; the endpoint accepts only classic tokens carrying repo.

    The message says "Resource not accessible by personal access token", which reads as a permission you forgot to tick — and the token already held Actions: read and write, the permission anyone would reach for. Nothing was under-scoped. It was the wrong kind of credential, and adding permissions to it could never have worked. With a classic token the same button promoted run #12, and GitHub's own record reads vamsiatluri approved — "Approved from Slack by vamsi.d.atluri": the approval is attributed to the token's owner, with the human who actually clicked carried in the comment. Traceable, and still weaker than GitHub's own gate.

    And a second one, found by a job failing The pipeline's notification step died with unknown status: awaiting. The branch that builds the message carrying the button had never been committed — it lived only on the author's laptop, along with the approval function itself and its template. Every earlier message in the channel had been posted by hand; the pipeline had never once sent one. Nothing failed loudly, because the function was deployed and working — it simply was not in the repository that is meant to BE the evidence. Deployed is not committed, and running infrastructure is not a record of itself. Fixed, and the message above is the first the pipeline has sent on its own.

    What is deployed

    Four small programs, each fronted by a named pointer called live. A rollback is moving that pointer back — one command, no rebuild.

    ProgramEnvironmentlive points atCommitFingerprint

    Both pairs now report an identical fingerprint. The pointer named live is what separates them — and moving it back is also how a rollback works. When the gate is released, each pair reports an identical fingerprint, which is what makes "we shipped what we tested" a measurement rather than a claim.

    Live endpoints

    Public, no sign-in. Open them and you are reading the deployed system directly.

    Why it is built this way

    Build once, deploy many

    Production has no build step. It deploys the artifact test already exercised, and both environments read the deployed fingerprint back and fail if it differs. "We shipped what we tested" is a check, not a hope.

    No stored cloud key

    The pipeline proves its identity each run and receives a pass that expires within the hour. There is no permanent credential to leak and none to rotate.

    A rollback that takes seconds

    Each deploy freezes a numbered version; the pointer named live selects one. Rolling back moves the pointer. Nothing is rebuilt and no pipeline runs.

    The checks run against the real thing

    The same suite runs on a laptop, after every deploy, and on a schedule. Four of the bugs found in this project only failed against a real deployment — none would have surfaced locally.
